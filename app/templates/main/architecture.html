CRYPTOGRAPHIC ARCHITECTURE

AUTHENTICATED ACCESS ONLY SYSTEM SPECIFICATION

An engineering summary of how VaultPay protects user identity, ensures financial ledger precision, encrypts sensitive payment instruments at rest, and verifies cryptographic integrity during data retrieval.

👤 1. Identity & Access

Salted SHA-256 with 256-bit cryptographically random salt per user. Timing-safe verification, sliding-window rate limiting, and session fixation defense.

💳 2. Sensitive Vault (AEAD)

AES-256-GCM authenticated encryption at rest with 12-byte random nonces and 16-byte GMAC authentication tags bound to user PIN context.

Exact 64-bit integer paise arithmetic (eliminating binary float errors) paired with canonical JSON deterministic SHA-256 integrity fingerprinting.

Flow 1

User Identity & Password Storage

Table: users

Storage Pipeline (Registration)

  1. Salt Generation: A unique 256-bit (32-byte) cryptographically secure salt is generated using secrets.token_bytes(32) for each individual account.
  2. Digest Computation: Password string and salt bytes are concatenated and hashed via SHA-256:
    hash = hashlib.sha256(password + salt).hexdigest()
  3. Database Persistence: Only password_hash (64 hex characters) and salt (64 hex characters) are written to SQLite.
  4. Zero Plaintext Retention: Plaintext passwords are wiped from memory and never logged or serialized.

Verification Pipeline (Login)

  1. User provides username/email and password over TLS.
  2. Server retrieves the user's stored salt and re-hashes the entered password.
  3. Constant-Time Verification: Evaluated using hmac.compare_digest(computed_hash, stored_hash) to eliminate timing side-channel attacks.
  4. Session Fixation Defense: Flask session identifier is regenerated upon successful authentication via session.clear() and session.modified = True.
Flow 2

Sensitive Payment Instrument Encryption (AES-256-GCM AEAD)

Table: payment_methods

VaultPay uses Authenticated Encryption with Associated Data (AEAD) via AES-256 in Galois/Counter Mode (GCM). Unlike basic CBC or ECB encryption, GCM guarantees both confidentiality (encryption) and authenticity (tamper-proofing).

Flow 3

Decryption & Step-Up Reveal Verification

Challenge Gate: /reveal

Decryption Pipeline

  1. Authorization Gate: Plaintext metadata is never exposed on standard GET requests. Accessing /reveal renders a step-up challenge gate.
  2. Two-Factor Verification: User must provide account password + 4-digit security PIN.
  3. Reconstruct AAD Context: The server reconstructs the exact Associated Authenticated Data from the verified user session and PIN hash.
  4. Cryptographic Authentication: AESGCM.decrypt(nonce, ciphertext + tag, aad) checks the 16-byte tag.
  5. Tamper Rejection: If even 1 bit of ciphertext, tag, nonce, or AAD has been modified, Python's InvalidTag exception is raised and access is denied.

Decryption Decision Tree

IF (Password Valid AND PIN Valid):
Reconstruct AAD & Attempt AESGCM.decrypt()
✓ Tag Valid ➔ Return Decrypted Data
✕ InvalidTag ➔ 400 Bad Request (Tampered)
ELSE:
Reject with 401 Unauthorized (Gate Locked)
Flow 4

Financial Precision & Transaction Ledger Integrity

Tables: wallets, transactions
Integer Paise Accounting (Zero Float Error)

Standard floating-point numbers cannot accurately represent base-10 decimals (e.g. 0.1 + 0.2 = 0.30000000000000004). VaultPay enforces strict integer arithmetic:

  • All balance amounts are stored as 64-bit integer paise (1 INR = 100 paise).
  • ₹150.00 is stored internally as 15000 paise.
  • Arithmetic is exact: balance = balance - transfer_cents.
Atomic Transactions & SHA-256 Ledger Fingerprint

Ledger mutations follow ACID guarantees:

  • Atomic Commit: Debit from sender and credit to recipient execute within a single database transaction. If any error occurs, the entire state rolls back.
  • Canonical JSON Digest: Transaction attributes are serialized deterministically (keys sorted, compact separators) and fingerprinted via SHA-256 to ensure immutable audit trails.
